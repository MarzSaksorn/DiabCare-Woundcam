# DiabCare Android Companion ↔ Web Backend Integration Guide

## 1. Purpose

This guide defines how the native Android companion should connect the UNI-T UTi120M thermal camera to the DiabCare web application.

The companion owns hardware access. The web application owns clinician workflows, patient records, wound-assessment assignment, audit history, and protected storage.

```text
UNI-T UTi120M
    ↓ USB-C / Android USB Host
DiabCare Thermal Companion
    ├─ USB transport
    ├─ frame parsing
    ├─ calibration and radiometric conversion
    ├─ local preview
    └─ authenticated HTTPS client
             ↓
DiabCare web backend
    ├─ authentication and authorization
    ├─ thermal-capture validation
    ├─ protected object storage
    ├─ Supabase metadata
    └─ patient record / audit history
```

The current Android app is a **raw-frame transport and preview slice**. It parses 120 × 90 Y16 frames and renders a false-color raw-count preview. It does not yet perform calibration, produce Celsius values, or upload captures.

## 2. Current backend contracts

The web backend is a React/tRPC application. The router is in `server/routers.ts`, and protected procedures require an authenticated context.

The current API is mounted under the tRPC gateway, normally:

```text
POST /api/trpc/<procedure-name>
```

The exact request envelope and batching behavior are generated by the existing tRPC client in `client/src/lib/trpc.ts`. The Android client should either use a compatible tRPC HTTP client or call a dedicated REST upload endpoint added for the companion. Do not invent a second request envelope without documenting it on both sides.

### Existing relevant procedures

| Procedure | Current purpose | Companion suitability |
|---|---|---|
| `auth.me` | Read the current authenticated user | Useful after authentication |
| `diabetes.registeredPatients` | List active registered patients | Useful for patient selection, with pagination improvements recommended |
| `diabetes.registeredPatientRecord` | Read one patient record | Useful for confirmation before capture assignment |
| `diabetes.photoHistory` | Filter wound-photo history by patient/date | Useful after thermal records have a compatible media representation |
| `diabetes.uploadWoundPhoto` | Upload JPEG, PNG, or WebP wound photos as base64 | RGB-only; do not use for radiometric thermal captures |
| `diabetes.addWoundAssessment` | Create a wound assessment | Keep clinician-driven; the companion should not create assessments implicitly |
| `wound.infer` | Run RGB wound inference | Do not send thermal images unless a separate thermal model is trained and validated |

The current `uploadWoundPhoto` input is approximately:

```ts
{
  patientId: number;
  woundAssessmentId?: number | null;
  fileName: string;
  mimeType: "image/jpeg" | "image/png" | "image/webp";
  capturedAt: string; // timezone-aware timestamp
  caption?: string | null;
  imageData: string; // base64 or data URL
}
```

The server validates the base64 payload, limits the decoded image to 12 MB, stores image bytes through managed object storage, saves metadata in `patient_wound_media`, and writes an audit event. This is suitable for an exported Thermal Mobile JPEG fallback, but it does not preserve a temperature matrix, calibration version, or measurement metadata.

## 3. Required backend additions

Add a dedicated thermal domain instead of overloading `uploadWoundPhoto`.

Recommended procedures or routes:

```text
thermal.createUploadSession
thermal.uploadCapture
thermal.getCapture
thermal.listPatientCaptures
thermal.getRadiometricArtifact
thermal.cancelUpload
```

A REST upload route is preferable for large binary payloads. If tRPC remains the transport, use a dedicated procedure with a documented multipart or presigned-upload strategy. Avoid placing a large temperature matrix and image bytes into one JSON request.

### Recommended storage flow

1. Android requests an upload session.
2. The backend authenticates the clinician and validates patient access.
3. The backend returns short-lived upload URLs or an upload token for the preview image and radiometric matrix artifact.
4. Android uploads bytes directly to protected object storage.
5. Android calls `finalize` with hashes and metadata.
6. The backend verifies object existence, size, MIME type, dimensions, and hashes.
7. The backend writes the thermal capture row and audit event in one transaction.

This keeps base64 image and matrix data out of the tRPC JSON envelope and avoids unnecessary memory amplification in Node.js.

## 4. Thermal capture contract

Use UTC timestamps at the API boundary. Android may display local time, but it must send an ISO-8601 timestamp with an explicit offset or `Z`.

The server must reject finalization when the matrix is not exactly 120 × 90, the encoding is unknown, the unit is missing, the calibration version is absent, the uploaded hashes do not match, or the required storage objects are unavailable.

## 5. Authentication design

### Current limitation

The current web backend authenticates protected tRPC procedures through the server-side session context in `server/_core/context.ts`. The browser receives a session cookie through the existing Manus OAuth flow. The Android companion does not currently have a documented native login or bearer-token endpoint.

Do not copy the browser cookie, use the Supabase database password, embed `SUPABASE_DATABASE_URL`, or ship a server secret in the APK.

### Recommended companion pairing flow

Add a short-lived pairing flow to the backend:

1. A signed-in clinician opens **Connect companion** in the web app.
2. The web app requests a one-time pairing code from the backend.
3. The code expires after five minutes and can be used once.
4. The Android app displays or scans the code.
5. The backend exchanges the code for a device-scoped access token and refresh token.
6. The Android app stores tokens in Android Keystore-backed encrypted storage.
7. The backend associates the token with the clinician, device ID, and organization scope.
8. The web app shows active devices and offers revoke access.

Use a separate token scope such as:

```text
thermal:capture:create
thermal:capture:read
patient:read:assigned
```

The token must not grant unrestricted database access. Enforce patient authorization on every capture session and finalization request.

For an early local-only prototype, a manually entered development token may be used on a non-production server. Never use `LOCAL_AUTH_BYPASS` in production and never embed that bypass in a release APK.

## 6. Android implementation plan

The current companion uses Java, Android USB Host APIs, Gradle, min SDK 26, and target SDK 35. Keep the network layer separate from the USB layer.

Recommended modules:

```text
com.diabcare.thermal
├─ Uti120Protocol.java       // frame wire format
├─ Uti120UsbBridge.java      // USB permission and I/O
├─ ThermalPreviewView.java   // local raw preview
├─ CompanionAuthClient.java  // pairing and token refresh
├─ ThermalCaptureClient.java // session, upload, finalize
└─ CaptureRepository.java    // pending/offline capture state
```

Use a maintained HTTPS client such as OkHttp. Add certificate validation through the platform trust store. Use a network security configuration only when a local development server requires it; do not disable TLS verification in production.

### Upload client sequence

```java
// Pseudocode; keep real code off the UI thread.
String accessToken = authClient.getValidAccessToken();
UploadSession session = captureClient.createSession(
    accessToken,
    patientId,
    woundAssessmentId,
    captureMetadata,
    artifactManifest
);

captureClient.put(session.previewUrl, previewPngBytes, "image/png");
captureClient.put(session.radiometricUrl, float32LittleEndianMap, "application/octet-stream");

ThermalCapture saved = captureClient.finalizeCapture(
    accessToken,
    session.captureId,
    hashes,
    statistics,
    calibrationMetadata
);
```

Use a WorkManager-backed queue for uploads. A capture should move through explicit states:

```text
LOCAL_ONLY → UPLOAD_SESSION_CREATED → ARTIFACTS_UPLOADING
→ FINALIZING → SAVED
```

Failure states should preserve the local artifact and show a retry action:

```text
UPLOAD_FAILED → RETRYING
FINALIZE_FAILED → NEEDS_REVIEW
EXPIRED_SESSION → CREATE_NEW_SESSION
```

Do not silently delete a capture after a network failure.

## 7. Patient assignment workflow

The companion should not accept an arbitrary patient ID without confirmation.

Recommended flow:

1. Fetch a limited, authorized patient list or scan a patient QR code generated by the web app.
2. Search by local patient code, not by broad unmasked name search when possible.
3. Show patient code, internal ID, display name according to privacy policy, and registration location.
4. Load available wound assessments for the selected patient.
5. Show a confirmation card containing patient, wound label, assessment date, capture timestamp, and device status.
6. Require an explicit **Save thermal capture** action.
7. Record the assignment and clinician identity in the backend audit event.

If the companion is offline, store only a local pending assignment and require revalidation when reconnecting. Do not assume a patient ID remains valid forever.

## 8. Database additions

Add a dedicated table rather than putting thermal metadata into `patient_wound_media`.

Suggested table:

```sql
create table patient_thermal_captures (
  id bigint generated by default as identity primary key,
  patient_id bigint not null references registered_patients(id),
  wound_assessment_id bigint references patient_wound_assessments(id),
  preview_storage_key text not null unique,
  radiometric_storage_key text not null unique,
  captured_at timestamptz not null,
  width integer not null check (width = 120),
  height integer not null check (height = 90),
  unit varchar(8) not null check (unit = 'C'),
  min_temperature_c numeric(8,3),
  max_temperature_c numeric(8,3),
  mean_temperature_c numeric(8,3),
  roi_mean_temperature_c numeric(8,3),
  reference_mean_temperature_c numeric(8,3),
  roi_delta_temperature_c numeric(8,3),
  emissivity numeric(5,4),
  ambient_temperature_c numeric(8,3),
  distance_m numeric(8,3),
  fpa_temperature_c numeric(8,3),
  shutter_temperature_c numeric(8,3),
  lens_temperature_c numeric(8,3),
  frame_counter integer,
  device_serial varchar(160),
  calibration_version varchar(80) not null,
  bridge_version varchar(80) not null,
  recorded_by_user_id bigint references users(id) on delete set null,
  created_at timestamptz not null default now()
);

create index patient_thermal_captures_patient_date_idx
  on patient_thermal_captures(patient_id, captured_at desc);
```

Enable Row Level Security in Supabase and keep the service-role write path server-side. The Android app must never receive database credentials or object-storage master keys.

## 9. Security requirements

- Require HTTPS for every production request.
- Use short-lived access tokens and refresh-token rotation.
- Store tokens in Android Keystore-backed encrypted storage.
- Revoke lost devices from the web app.
- Bind every capture to an authenticated clinician and authorized patient.
- Validate file size, MIME type, dimensions, encoding, hashes, and timestamps server-side.
- Reject timestamps too far in the future or outside the permitted capture window.
- Keep object keys opaque; do not put patient names in filenames or URLs.
- Write audit events for pairing, capture creation, finalization, retry, hide, delete, and revoke actions.
- Log identifiers and errors, not raw patient data or full thermal matrices.
- Avoid analytics SDKs and external image services for patient thermal data.

## 10. Offline and retry behavior

Village-clinic connectivity may be intermittent. The companion should support local encrypted pending captures, but this is not permission to keep unprotected health data indefinitely.

Set a configurable retention period for unsent captures. Show the clinician whether a capture is saved locally, uploaded, or finalized in DiabCare. Use content hashes and an idempotency key so retrying a finalize request cannot create duplicate records.

Recommended idempotency key:

```text
sha256(deviceSerial + frameCounter + capturedAt + previewSha256)
```

The backend should enforce uniqueness on the idempotency key or capture fingerprint.

## 11. Error contract

Return stable machine-readable errors:

| Code | Meaning | Android behavior |
|---|---|---|
| `AUTH_REQUIRED` | Token missing or expired | Refresh or restart pairing |
| `FORBIDDEN_PATIENT` | Clinician cannot access patient | Remove assignment and show permission message |
| `CAPTURE_EXPIRED` | Upload session expired | Create a new session; keep local artifact |
| `ARTIFACT_HASH_MISMATCH` | Uploaded bytes differ | Do not finalize; retry upload |
| `INVALID_THERMAL_MATRIX` | Wrong dimensions or encoding | Mark capture invalid; do not retry unchanged bytes |
| `CALIBRATION_REQUIRED` | Capture lacks accepted calibration | Keep as raw preview only |
| `DUPLICATE_CAPTURE` | Same idempotency key already finalized | Treat as success and fetch existing record |
| `SERVER_UNAVAILABLE` | Temporary backend failure | Queue retry with backoff |

## 12. Delivery phases

### Phase 1: backend pairing and health

Add device pairing, token revocation, a protected health endpoint, and a companion connectivity status. Do not upload patient data yet.

### Phase 2: thermal upload without clinical measurement

Upload a false-color preview and raw frame artifact as **raw hardware validation data**. Keep the UI label explicit and do not show Celsius measurements.

### Phase 3: calibration and radiometric capture

Implement calibration-package parsing, shutter/NUC correction, Celsius conversion, matrix validation, and metadata persistence. Compare readings against Thermal Mobile or a trusted instrument.

### Phase 4: patient assignment and record display

Add wound-assessment selection, confirmation, capture history, audit events, and protected patient-record rendering in English and Thai.

### Phase 5: thermal decision support

Only after paired data and clinical review should the team consider ROI trends or a thermal-specific ML model. Keep every model output labeled **Decision Support** and require clinician judgment.

## 13. Acceptance criteria

The integration is ready for pilot testing when:

- An Android device can pair and revoke access without exposing a database secret.
- A connected UTi120M can produce a local preview without blocking the UI.
- A capture survives temporary network loss and retries without duplicates.
- The backend verifies artifact hashes and rejects malformed matrices.
- A clinician must confirm patient and wound assessment before saving.
- The saved capture displays in the correct patient record with UTC capture time, device metadata, calibration version, and audit history.
- Hidden or deleted media follows the same access and audit rules as existing wound photos.
- Raw preview data is never presented as Celsius.
- The complete flow passes on a real Android device and physical UTi120M, not only in a Gradle build.
